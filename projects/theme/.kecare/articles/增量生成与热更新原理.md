# Kecare 增量生成与热更新原理

## 一、概述

传统流程下，每改一个字都要 `kecare gen` 全量重跑：扫描所有文章 → 解析 Markdown → AI 翻译 → 写所有页面。这在文章多、需要翻译时非常慢。

`kecare dev` 解决三件事：

1. **自动检测变动**：监听 `.kecare/articles` 目录，文章一保存就感知。
2. **增量生成**：只对真正变更的文章做解析/翻译/写盘，未变文章复用缓存。
3. **热更新**：生成的 `.vue` / `.json` 文件被 Nuxt 开发服务器自动监听，写入即触发 HMR，浏览器无刷新更新。

```
kecare dev 启动
   │
   ├─ 1. 初始全量 gen（保证产物齐全）
   ├─ 2. 启动 fs.watch 监听 articles 目录
   └─ 3. 持续运行，等待文件变更事件
              │
              ├─ 文件保存 → debounce 400ms → 增量周期
              │     ├─ prune 孤儿产物
              │     ├─ runGeneration（命中缓存的文章跳过实活）
              │     └─ 写入 .vue / .json
              │           │
              │           └─ Nuxt HMR 监听到文件变化 → 浏览器热更新
              │
              └─ Ctrl+C → 关闭 watcher、停止 nuxt、退出
```

## 二、增量生成原理

### 2.1 思路：复用缓存，而非新建增量记账

增量生成要回答一个问题：**一篇文章是否需要重新处理？**

Kecare 没有另建一套"变更追踪"机制，而是复用已有的 `markdown-manifest.json` 内容哈希缓存。每次变更后，创建一个全新的 `KecareContext` 重跑完整的生成流程，由缓存层决定哪些文章走"快路径"、哪些走"慢路径"。

为什么这样做？dev 周期与 `gen` 命令走同一条管线 `run-generation.ts`，没有两套生成逻辑。下游聚合页（列表/归档/搜索）本来就需要全量数据，全流程重跑能保证聚合不出错。开销方面——缓存命中后最贵的环节（Markdown 解析、AI 翻译、磁盘写入）全部跳过，剩下的只是内存收集。

### 2.2 缓存机制：`markdown-manifest.json`

每篇文章的元数据与解析结果缓存在 `.kecare/cache/markdown-manifest.json`：

```json
{
  "version": 1,
  "articles": {
    "/花月.md": {
      "contentHash": "a1b2c3...",
      "variants": [
        {
          "lang": "zh-CN",
          "title": "花月",
          "html": "<div class=\"kecare\">...</div>",
          "hash": "6fb77dde",
          "__REAL_FS_PATHS__": ".../app/pages/articles/zh-CN/6fb77dde.vue",
          "...": "其它字段"
        }
      ]
    }
  }
}
```

- **`contentHash`**：文章原始内容的哈希（`Bun.hash.xxHash3(rawContent, 5678n)`）
- **`variants`**：该文章各语言版本的解析结果（含翻译后的 HTML、生成文件路径 `__REAL_FS_PATHS__` 等）。

### 2.3 命中判定：快路径 vs 慢路径

每篇文章处理时，先读原始内容算哈希，再与 manifest 中的缓存比较。

```ts
const contentHash = Bun.hash.xxHash3(rawContent, 5678n).toString(16);
const cached = manifest.articles[relativePath];
if (
    cached?.contentHash === contentHash          // ① 内容哈希一致
    && Array.isArray(cached.variants)
    && cached.variants.length > 0
    && cached.variants.every((article) =>        // ② 生成的 .vue 文件仍存在
        article.__REAL_FS_PATHS__ && existsSync(article.__REAL_FS_PATHS__)
    )
) {
    // 快路径：命中缓存
    for (const cachedArticle of cached.variants) {
        await emitArticleHandle(context, {
            ...cachedArticle,
            __SKIP_ARTICLE_GENERATOR__: true,     // 跳过 .vue 写盘
        });
    }
    return;
}
// 慢路径：缓存未命中，重新解析 Markdown / 翻译 / 写盘
```

**快路径（命中缓存）跳过的环节**：
- ❌ Markdown 解析（marked + 扩展）
- ❌ AI 翻译（最贵，需网络调用）
- ❌ 文章详情页 `.vue` 写盘

**快路径仍会做的环节**（廉价，纯内存）：

- ✅ 把缓存变体送入列表/归档/搜索处理器的 `handle()`，收集到内存聚合数据

**慢路径（未命中）做的环节**：

- ✅ 重新解析 frontmatter、Markdown → HTML
- ✅ 非原始语言走 AI 翻译（翻译本身还有**段落级缓存**，未变段落不重新翻译）
- ✅ 写文章详情页 `.vue`
- ✅ 更新 manifest 缓存

> 命中判定第 ② 条值得注意：即使哈希一致，但若生成的 `.vue` 被手动删除，也会判为未命中而重新生成。这让 dev 期间删除产物能自愈。

### 2.4 增量周期流程

一次文件变更触发的周期

```
runDevCycle()
  │
  ├─ pruneOrphans(projectPath)     // ① 清理被删文章的孤儿产物
  │
  └─ runGeneration(projectPath)    // ② 重跑全流程
        │
        └─ executeInputDrivers(context)
              │
              ├─ markdownInputDriver          // 扫描所有 .md
              │     ├─ 未变文章 → 命中缓存（快路径）
              │     └─ 变更文章 → 重新解析+翻译+写 .vue（慢路径）
              │
              ├─ useMenuModuleHandler.finish  // 重建菜单
              └─ emitModuleFinish             // 重建聚合页
                    ├─ list.finish      → 写列表页（分页）
                    ├─ search.finish    → 写 search-index.json
                    └─ archives.finish  → 写归档页
```

**为什么聚合页每次都全量重算？** 列表分页、归档、搜索索引都跨文章聚合，改一篇文章可能影响分页边界。全量重算保证正确性，且只写少量文件，开销可忽略。真正昂贵的是 AI 翻译，已被缓存挡掉。

### 2.5 状态隔离：为什么不会污染

所有模块处理器都用 `WeakMap<KecareContext, 实例>` 缓存实例

每次 `runGeneration` 都创建**全新的 `KecareContext`**。新 context → WeakMap 取不到旧实例 → 创建全新处理器 → 全新内部状态。因此 dev 多个周期之间不会出现上一轮数据污染下一轮。

## 三、文章变动检测

### 3.1 监听器：`fs.watch` recursive

使用 Node 标准库的 `fs.watch` 监听文章目录：

```ts
const watcher = watch(articlesDir, { recursive: true }, (_eventType, filename) => {
    if (!filename) return;
    const name = filename.toString();
    // 只关注 markdown 文件；编辑器临时文件（.md~、.swp、.tmp 等）无 .md 后缀自然被过滤
    if (!/\.(md|mdx|markdown)$/i.test(name)) return;
    scheduleCycle();
});
```

- **`recursive: true`**：递归监听子目录，Windows 原生支持（ReadDirectoryChangesW），Bun 兼容。
- **事件类型**：`change`（内容修改）和 `rename`（新增/删除/重命名）都触发。
- **文件过滤**：只处理 `.md`/`.mdx`/`.markdown`。编辑器原子保存产生的临时文件（`file.md~`、`file.md.swp`、`.tmp`）后缀不符，自动忽略。

> 没有引入 `chokidar` 等第三方监听库，保持依赖精简，`node:fs` 已满足需求。

### 3.2 debounce：合并连续保存事件

编辑器保存时常触发 2-3 次事件（写入 + 元数据更新）。用 400ms debounce 合并为一次重生成：

```ts
const scheduleCycle = () => {
    if (debounceTimer) clearTimeout(debounceTimer);
    debounceTimer = setTimeout(() => {
        debounceTimer = null;
        runDevCycle();
    }, 400);
};
```

每次事件都重置定时器，只有 400ms 内无新事件才真正触发周期。

### 3.3 防并发：running / dirty 双标志

一次增量周期可能耗时（变更文章多或需翻译时）。若周期运行中又有新事件，不能并发跑（会同时读写 manifest、同时写同一文件）。用双标志解决：

```ts
const runDevCycle = async () => {
    if (running) {
        dirty = true;        // 周期运行中，标记脏，直接返回
        return;
    }
    running = true;
    try {
        await pruneOrphans(projectPath);
        await runGeneration(projectPath);
    } catch (error) {
        consola.error('增量重生成失败:', ...);   // 错误被吞，不中断 watcher
    } finally {
        running = false;
        if (dirty) {          // 周期结束时有累积的变更，再跑一次
            dirty = false;
            runDevCycle();
        }
    }
};
```

- **`running`**：当前是否有周期在跑。有则新事件只置 dirty。
- **`dirty`**：周期运行中是否又收到变更。周期结束检查 dirty，决定是否立即再跑一轮。

这保证了：任意时刻最多一个周期在跑，且最后一次变更一定会被处理。

### 3.4 错误隔离

周期的 `try/catch` 捕获所有错误并打印，不会让 watcher 崩溃。即便某篇文章 frontmatter 格式错误、翻译 API 失败，dev 仍继续监听，修好文件后下一周期恢复正常。

## 四、热更新机制（本地服务器不停止）

核心问题是：kecare 重新生成文件后，Nuxt 开发服务器不用重启就能在浏览器看到更新，这是怎么做到的？

### 4.1 原理：Nuxt HMR 自动监听产物文件

Nuxt 的开发服务器（`nuxt dev`）内置 Vite，Vite 会监听项目目录下的源文件变化。Kecare 生成的产物恰好落在 Nuxt 监听的范围内：

| 产物 | 路径 | Nuxt 行为 |
|---|---|---|
| 文章详情页 | `app/pages/articles/<lang>/<hash>.vue` | Vite 监听 `.vue` 文件，写入即触发 HMR，组件热替换 |
| 列表/归档页 | `app/pages/*.vue` | 同上 |
| 搜索索引 | `public/articles/*.json` | 静态资源，前端重新 fetch 即拿到新数据 |

kecare 不需要主动通知 Nuxt。只要把文件写到这些路径，Nuxt 的文件监听器自然会感知并推送 HMR 更新到浏览器。两者通过文件系统这一"中介"解耦通信。

```
kecare dev 进程                Nuxt dev 进程
     │                              │
     ├─ 检测到 花月.md 变更          │
     ├─ 重新生成 .vue 文件 ────────→ 文件系统
     │                              ├─ Vite 监听到 .vue 变化
     │                              ├─ 编译新模块
     │                              └─ WebSocket 推送 HMR → 浏览器热更新
```

### 4.2 两种进程模型

#### 模型 A：解耦模式（默认）

```bash
kecare dev ./projects/theme
```

kecare 只运行监听器。用户在**另一个终端**运行 `nuxt dev`。两个独立进程通过文件系统通信。

- ✅ 互不影响：一方崩溃另一方还在。
- ✅ 日志分离，排查方便。
- 适合长期开发。

#### 模型 B：合并模式（`--with-nuxt`）

```bash
kecare dev ./projects/theme --with-nuxt
```

kecare 用 `Bun.spawn` 拉起 `nuxt dev` 子进程，统一管理：

```ts
childProc = Bun.spawn(['bun', 'run', 'dev'], {
    cwd: projectPath,
    stdio: ['inherit', 'inherit', 'inherit'],   // 共享终端输出
});
```

- 一条命令搞定。
- Ctrl+C 时 kecare 会先 `childProc.kill()` 杀掉 nuxt 再退出。
- 两个进程的日志会交错显示在同一终端。

### 4.3 启动顺序保证

dev 命令**先跑一次初始全量 gen，再启动 nuxt**：

```
1. runGeneration(projectPath)   // 初始 gen，产物就位
2. 若 --with-nuxt：启动 nuxt dev // nuxt 启动时页面已存在，不会报 404
3. 启动 fs.watch                 // 开始监听后续变更
```

这保证 `--with-nuxt` 时 nuxt 启动那一刻所有 `.vue` 页面已生成，不会因缺页面报错。

### 4.4 为什么"不停止服务器"

热更新是文件级别的热替换，不是进程重启：

- Nuxt dev 进程始终运行，持有 Vite 编译器状态和 WebSocket 连接。
- kecare 写入新 `.vue` → Vite 的文件监听器（`chokidar` 内部）收到 `change` 事件 → Vite 重新编译该模块 → 通过 WebSocket 推送 HMR 更新 → 浏览器替换组件，不刷新页面。
- 整个过程 Nuxt 进程没有重启，前端状态（滚动位置、输入、菜单展开等）得以保留。

kecare 进程同样不重启，它只是反复跑 `runGeneration`，每次写文件后立即继续监听。

## 五、prune：孤儿产物清理

文章被删除或重命名时，旧的生成文件（`.vue`）不会被新流程覆盖（因为新流程扫不到它），会变成"孤儿"。dev 周期开始时先跑 `pruneOrphans` 清理：

```
1. 读 manifest
2. glob 当前实际存在的 .md 文件，算出 relativePath 集合
3. 遍历 manifest.articles 的 key：
     若 key 不在当前集合（说明文章被删/改名）：
       ├─ 删除该 entry 所有 variant 的 __REAL_FS_PATHS__ 指向的 .vue 文件
       └─ 从 manifest 删除该 entry
4. 有变更则写回 manifest
```

`relativePath` 计算hash完全一致（`fsPath.replace(articlePath, '')`），保证 key 能对上。

## 六、完整时序示例

以"修改 `花月.md` 一个字"为例：

```
T0   用户在编辑器保存 花月.md
T0   fs.watch 收到 change 事件 → scheduleCycle() 重置 400ms 定时器
T0.4 定时器触发 → runDevCycle()
       │
       ├─ running=false → 置 running=true
       ├─ pruneOrphans：花月.md 仍存在，无需清理
       ├─ runGeneration：
       │    ├─ 新建 KecareContext
       │    ├─ 扫描所有 .md
       │    │    ├─ 花月.md：contentHash 变了 → 未命中
       │    │    │    ├─ 重新解析 Markdown
       │    │    │    ├─ 原语言 zh-CN：直接 marked → HTML
       │    │    │    ├─ en-US / ja-JP：AI 翻译（未变段落命中翻译缓存）
       │    │    │    ├─ 写 app/pages/articles/zh-CN/<hash>.vue  ← 文件变化
       │    │    │    └─ 更新 manifest
       │    │    └─ 其它文章：contentHash 一致 → 命中缓存，跳过
       │    ├─ 重建菜单 .menu.generated.ts
       │    └─ 重建列表/归档/搜索页
       ├─ running=false
       └─ "增量重生成完成"

T1   Vite 监听到 .vue 文件变化 → HMR 推送 → 浏览器热更新（页面不刷新）
```

## 七、边界场景

| 场景 | 行为 |
|---|---|
| 新增 `.md` | 缓存未命中 → 全流程生成 |
| 修改 `.md` 内容 | 哈希变 → 未命中 → 重新解析；翻译按段落缓存，未变段落不重译 |
| 删除 `.md` | prune 删除孤儿 `.vue` + 清理 manifest entry |
| 重命名 `.md` | 等同删旧加新；旧 `.vue` 被 prune 清理；新 hash 不同 → URL 变 |
| `hidden: true` | markdown-driver 删 manifest entry 前先删 `.vue`，gen/dev 都生效 |
| 周期运行中再次保存 | running/dirty 标志 → 当前周期结束后再跑一轮 |
| 文章解析/翻译失败 | try/catch 吞错并打印，watcher 不中断 |
| 生成的 `.vue` 被手动删 | 命中判定的 existsSync 失败 → 判为未命中 → 自愈重生成 |

## 八、已知限制

1. **模板/菜单/配置变更不监听**：`kecare dev` 只监听 `.kecare/articles`。修改 `*.article.ts`、`*.list.ts`、`*.menu.source.ts`、`kecare.config.ts` 不会触发生成。原因是这些文件通过 `await import()` 动态加载，Bun 的模块缓存导致同进程内重跑也用旧模板。
   - 解决：改模板/菜单/配置后，重启 `kecare dev`（或手动跑一次 `kecare gen`）。
